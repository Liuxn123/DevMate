

# DevMate V1 技术架构设计说明书
**项目名称：** DevMate Agent  
**架构类型：** Windows 本地模块化单体应用  
**文档版本：** V1.0  
**目标阶段：** MVP 开发与核心架构落地

## 设计目标与边界
DevMate 是一个面向开发人员的本地开发环境管理 Agent，核心目标是将一个新项目从 Git 仓库或本地目录导入，完成环境识别、依赖检查、运行环境准备、项目启动和错误修复，尽量减少开发人员手动配置环境的工作量。

V1 采用 Windows 11 作为首要运行平台。统一工具仓库负责保存 DevMate 管理的各版本开发工具、缓存与资源，项目级环境配置负责决定具体项目使用什么版本和路径。

V1 完整支持常规 Java + Maven 项目。DevMate 自身前端使用 Vue + Vite，Node.js/npm 是本产品的构建工具链；这不代表 V1 支持导入和部署 Node.js 用户项目。Node.js + npm 用户项目支持放到 V1.1。Gradle、Python、Docker 等通过扩展接口逐步接入。

主要架构原则：

+ 单体优先：不引入微服务、分布式调度、Redis、消息队列和多 Agent。
+ 确定性优先：环境识别、版本检查、任务执行与验证由程序实现，AI 不替代确定性逻辑。
+ 安全优先：Agent 不能直接执行任意 Shell 命令。
+ 人机协同：下载、安装、运行仓库脚本、修改配置等操作需要明确授权。
+ 可恢复性：任务状态持久化，重要配置修改前创建备份。
+ 可扩展性：工具安装、项目识别、故障诊断统一使用适配器接口。

## Java 后端模块设计
后端按业务能力划分包和模块，部署时保持一个 Spring Boot 进程。

| 模块 | 核心职责 | 主要组件 |
| --- | --- | --- |
| project | 项目导入、仓库管理、项目结构识别 | ProjectService、ProjectDetector |
| environment | V1 扫描 JDK、Maven；Node/npm 用户项目支持 V1.1 | EnvironmentScanner、ToolRegistry |
| installer | 下载、安装、版本校验、卸载和安装记录 | InstallService、InstallerAdapter |
| configuration | 全局路径、项目级配置、差异比较和备份 | ConfigService、ConfigBackupService |
| agent | 意图解析、上下文构建、诊断分析、方案生成 | AgentOrchestrator、DiagnosisService |
| task | 任务计划、调度、步骤状态、进度、取消 | TaskService、TaskScheduler |
| executor | 命令规范化、参数校验、受控进程执行 | CommandExecutor、ProcessManager |
| security | 权限规则、路径校验、操作审批、审计 | PolicyEngine、ApprovalService |
| logging | 执行日志、故障提取、诊断报告 | ExecutionLogService |
| common | 统一响应、异常处理、存储、基础工具类 | GlobalExceptionHandler、Repository |


模块依赖遵循业务层调用领域服务的原则。Agent 可以调用项目、环境、任务和诊断的受限接口，但不直接调用底层操作系统命令。

## Agent 架构设计
V1 采用单 Agent + 工具调用 + 显式工作流的混合模式。

Agent 内部划分逻辑角色，而不是启动多个独立 Agent：

**Intent Resolver：** 解析用户自然语言输入，识别操作目标、项目、预期结果。

**Context Builder：** 收集项目结构、当前环境、已安装工具版本、任务日志和历史上下文。

**Planner：** 根据诊断事实构造结构化执行建议，输出 PlanProposal。

**Diagnosis Analyzer：** 对命令错误与环境异常进行归类、解释与修复建议。

**Response Generator：** 向用户说明问题、执行计划、失败原因和下一步动作。

Agent 可以通过 Tool Calling 使用查询类工具，例如：

+ scan_environment：扫描本地开发环境。
+ inspect_project：识别项目类型与配置要求。
+ list_installed_tools：获取已安装工具版本。
+ inspect_dependencies：分析项目依赖配置。
+ get_task_logs：读取任务执行日志。
+ check_project_status：查询项目启动和运行状态。

涉及安装、修改和启动的操作，由 Agent 提出结构化动作请求，然后交给 Policy Engine、Task Service 和用户审批流程。

AI 生成的计划不得作为原始命令直接执行。必须转换为程序定义的 ActionType，并对参数进行 Schema、路径、权限和版本校验。

任务计划中的动作类型包括：

+ CLONE_REPOSITORY
+ INSTALL_TOOL
+ CONFIGURE_PROJECT
+ INSTALL_DEPENDENCIES
+ START_PROJECT
+ VERIFY_PROJECT
+ BACKUP_FILE
+ RESTORE_FILE

V1 不开放 `execute_arbitrary_command` 这样的通用执行工具。

模型对话通过 Spring AI ChatClient 实现；对于需要跨 HTTP 请求暂停审批的动作，采用业务层显式工作流控制工具执行，不依赖一次模型调用自动完成全部动作。

## 项目识别架构
项目识别采用规则引擎 + 可扩展 Detector 机制。

定义 ProjectDetector 接口，接收项目根目录和受限文件信息，返回项目类型、工具要求、配置清单与可用启动方式。

V1 识别 Java/Maven 项目。下表中的 Node.js 规则作为 V1.1 扩展；DevMate 自身 Vue 前端的构建不属于用户项目识别范围。

| 文件特征 | 项目类型 | 环境要求 |
| --- | --- | --- |
| pom.xml | Maven Java | JDK、Maven 或 Maven Wrapper |
| package.json | Node.js 项目（V1.1） | Node.js、npm 或声明的包管理器 |
| vite.config.* | Vite 前端（V1.1） | Node.js、npm、Vite |
| application.yml / properties | Spring Boot 配置线索 | 在 Maven 项目内进一步识别 |
| .nvmrc | Node 版本约束（V1.1） | 指定或兼容的 Node 版本 |
| .mvn / wrapper | Maven Wrapper | 项目指定的 Maven 分发版本 |


ProjectDetector 只识别和读取受限文件，不自动执行仓库提供的脚本。

项目可存在多个子模块，例如 backend、frontend。V1 使用简单的模块树表示；无法确定启动命令时，由用户选择模块和脚本，而不是让 AI 猜测后直接执行。

## 环境管理与版本隔离
采用统一工具仓库 + 项目级运行环境配置。

建议目录结构：

+ `D:\DevMate\tools`：JDK、Maven、Node 等管理工具。
+ `D:\DevMate\cache`：Maven、npm、安装包缓存。
+ `D:\DevMate\workspaces`：项目工作目录。
+ `D:\DevMate\config`：全局和项目运行配置。
+ `D:\DevMate\backups`：配置变更备份。
+ `D:\DevMate\logs`：应用与任务日志。
+ `D:\DevMate\data`：SQLite 数据库。

以上为示例根目录，安装时允许用户修改，不强制使用 D 盘。

环境扫描需同时识别系统已安装工具与 DevMate 自行管理的工具。前者可以直接复用，不要求重复安装；后者进行版本化管理。

项目执行前由 EnvironmentResolver 构建运行环境，例如：

+ 为选定 JDK 配置本次子进程的 JAVA_HOME。
+ 将对应工具 bin 目录添加到本次子进程 PATH 前部。
+ 为 Maven 指定项目适用的 settings.xml 和本地仓库路径。
+ 为 npm 指定受管缓存目录。
+ 记录项目实际使用的工具版本与路径。

默认仅修改当前任务的子进程环境，不直接覆盖 Windows 全局 PATH。

V1 为不同 Java 项目选择兼容的 JDK/Maven；项目级 Node.js 版本管理属于 V1.1。

## 任务计划与执行架构
Task 是执行工作的基本单元，由多个顺序 TaskStep 组成。V1 采用顺序步骤，暂不实现通用 DAG 调度。

任务生命周期：

CREATED → ANALYZING → PLAN_READY → AWAITING_APPROVAL → QUEUED → RUNNING → VERIFYING → SUCCEEDED

异常状态包括 FAILED、CANCELLED、INTERRUPTED 和 PARTIAL_SUCCESS。

Plan 需要包含：

+ 目标项目与工作目录。
+ 每个操作的 ActionType。
+ 所需工具、目标版本和下载来源。
+ 涉及的文件路径和预期配置修改。
+ 风险等级和审批要求。
+ 执行前置条件与验证标准。
+ 可回退操作及不可回退风险。

计划生成后生成不可变版本与内容哈希。用户批准的是该具体版本，不是任意后续操作。执行前必须重新校验环境、操作参数和审批有效性，检测到计划变化后要求重新审批。

TaskScheduler 从 SQLite 中领取等待任务，交给有限线程池执行。V1 可以采用全局单个变更任务运行、多个只读扫描并行的调度策略，降低文件及环境冲突。

同一项目同时只允许一个可能修改该项目的任务运行。执行使用项目级锁，必要时叠加工具安装目录锁。

进程由 ProcessManager 管理。采用 Java ProcessBuilder 指定可执行文件、参数数组、工作目录和环境变量，并统一处理：

+ 命令白名单与参数模板。
+ 进程启动、退出码检查。
+ 输出采集与实时进度推送。
+ 超时及用户取消。
+ 子进程树清理。
+ 日志大小限制与敏感字段脱敏。

不把大模型输出直接拼接为 PowerShell 或 CMD 字符串。对于 Maven Wrapper、npm scripts 等仓库自带脚本，需明确展示执行来源和风险，在用户确认后才启动。

## 智能诊断与修复
诊断采用规则优先、LLM 辅助的方案。

RuleDiagnoser 识别常见明确错误，包括：

+ JAVA_HOME 缺失或指向无效目录。
+ Java 编译版本不匹配。
+ Maven 命令不存在。
+ npm 或 Node.js 版本不满足约束（V1.1）。
+ Maven 依赖下载失败。
+ 端口被占用。
+ 项目启动命令退出异常。

规则命中时优先返回确定性结论。对于无法准确识别的问题，由 LLM 根据错误摘要、环境快照和任务上下文生成原因分析与修复建议。

每个诊断结果包含问题类型、证据、可能原因、建议操作、风险等级和验证方式。

修复动作仍需进入计划审批与执行流程，不允许诊断结果直接获得写文件或执行命令的能力。

单次修复后必须进行验证；如果修复失败，保存新的错误证据并向用户展示后续建议。V1 限制自动诊断与重试次数，防止无限循环。

## 数据模型设计
SQLite 负责存储项目、环境配置、任务状态、审批历史、对话和配置修改记录。长篇执行日志保存为本地文件，数据库保留日志索引与路径。

| 表名 | 核心字段 | 说明 |
| --- | --- | --- |
| dm_project | id、name、source_type、repo_url、root_path、project_type、created_at | 项目基本信息 |
| dm_project_module | id、project_id、module_path、module_type、run_profile_json | 项目子模块和运行配置 |
| dm_environment_profile | id、project_id、tools_json、paths_json、env_json、updated_at | 项目级环境配置 |
| dm_tool_install | id、tool_type、version、install_path、source、status、checksum | 已管理的工具安装记录 |
| dm_env_snapshot | id、project_id、snapshot_json、scanned_at | 环境扫描历史 |
| dm_task | id、project_id、type、status、plan_json、plan_hash、created_at、finished_at | 任务和已批准执行计划 |
| dm_task_step | id、task_id、step_order、action_type、params_json、status、exit_code、started_at、finished_at | 任务步骤 |
| dm_task_approval | id、task_id、plan_hash、scope_json、decision、decided_at | 审批记录 |
| dm_task_log | id、task_id、step_id、log_path、summary、created_at | 日志文件索引 |
| dm_file_change | id、task_id、file_path、before_hash、after_hash、backup_path、rollback_status | 文件修改和回退信息 |
| dm_chat_session | id、project_id、title、created_at、updated_at | Agent 会话 |
| dm_chat_message | id、session_id、role、content、created_at | 会话消息 |


采用 UUID 或雪花 ID 生成主键。时间使用统一时间格式，任务状态及动作类型使用枚举约束。

需要为任务状态、项目 ID、创建时间和任务步骤建立索引。任务状态更新采用事务及条件更新机制，防止重复领取和状态竞争。

工具安装路径、项目路径和配置文件路径需要规范化处理，避免路径越界。

数据库不保存模型 API Key 等明文凭据。敏感凭据使用操作系统安全存储或加密方案管理。

## API 设计
前端使用 REST API 操作项目、环境和任务，SSE 获取任务执行事件。

| 接口 | 方法 | 作用 |
| --- | --- | --- |
| /api/v1/environment/snapshot | GET | 获取当前环境 |
| /api/v1/environment/scan | POST | 发起环境扫描 |
| /api/v1/tools | GET | 查询工具版本与安装位置 |
| /api/v1/projects | POST | 导入项目 |
| /api/v1/projects/{id}/inspect | POST | 识别项目结构 |
| /api/v1/projects/{id}/profile | PUT | 保存项目运行配置 |
| /api/v1/tasks/plan | POST | 生成结构化任务计划 |
| /api/v1/tasks/{id}/approve | POST | 审批指定计划 |
| /api/v1/tasks/{id} | GET | 查看任务状态 |
| /api/v1/tasks/{id}/cancel | POST | 取消任务 |
| /api/v1/tasks/{id}/events | GET | SSE 订阅执行日志 |
| /api/v1/agent/sessions | POST | 创建 Agent 会话 |
| /api/v1/agent/sessions/{id}/messages | POST | 发送 Agent 消息 |


Agent 消息接口返回对话结果、诊断信息或可审批的计划引用；流式对话可增加 SSE 接口，但与实际任务事件保持独立。

## 核心业务流程
以用户输入 Git 仓库地址并要求启动项目为例。

**项目导入阶段**

系统校验仓库地址与目标路径，确认网络访问和克隆目标后执行 Git Clone。克隆完成后调用 ProjectDetector 识别项目模块、构建配置及工具要求。

**环境对比阶段**

EnvironmentScanner 收集可用工具版本，EnvironmentResolver 根据项目约束匹配工具。缺少兼容版本时生成安装建议，已有兼容版本则直接复用。

**方案生成阶段**

系统基于确定性检测结果生成任务候选步骤，Agent 辅助解释问题及选择合理方案。后端完成动作规范化、风险判定与参数校验，并向用户展示完整操作计划。

**用户审批阶段**

前端展示即将安装的工具、目标目录、下载来源、运行命令及可能修改的配置文件。用户确认后，后端将审批绑定到计划版本。

**执行与验证阶段**

TaskScheduler 调用 Executor 按顺序执行步骤。每步采集日志、输出退出码和执行状态。最后通过构建结果、进程状态、端口或健康接口验证启动结果。

**故障处理阶段**

若执行失败，先由 RuleDiagnoser 分类，再由 Agent 补充分析。系统输出修复计划、错误证据及可回退项。用户批准后创建新的修复任务。

**完成阶段**

保存项目环境配置、启动信息和任务记录。下一次启动可直接复用已有工具与配置，无须重新执行完整安装流程。

## 安全与回滚机制
DevMate 是本地环境管理工具，拥有较高的文件系统和进程操作能力，因此权限控制必须独立于大模型。

关键约束：

+ 默认仅监听 127.0.0.1。
+ 本地操作接口采用会话身份验证、Origin 校验及 CSRF 防护。
+ 所有修改型任务必须经过策略校验和明确授权。
+ 对用户输入及项目路径进行规范化、符号链接与重解析点检查。
+ 检查允许修改的目录范围，不允许默认写入系统敏感目录。
+ 执行操作必须使用后端定义的动作模板。
+ 仓库 README、源码、构建输出和错误日志均视为不可信内容。
+ 模型 API Key、环境变量中的凭据和其他敏感数据进行脱敏。
+ 不允许模型通过提示词绕过审批。
+ 需要管理员权限的操作由用户显式处理，程序不静默提权。

对于配置文件，采用执行前备份、修改后校验及失败时恢复的策略。

对于工具安装，采用临时下载目录、校验包完整性、解压到临时目录、验证成功后转移到目标版本目录的方式，尽量减少半安装状态。

需要明确：Git Clone、依赖安装和项目构建可能产生外部副作用，不能保证通用事务回滚。系统只承诺恢复自身记录和明确可恢复的配置变更，不承诺撤销所有第三方脚本副作用。

任务恢复采用保守策略。应用异常关闭后，将运行中的任务标记为 INTERRUPTED，重启后重新检查执行结果，由用户选择重试或清理，而不是直接重放安装和修改动作。

## 系统部署与运行
V1 采用本地单机部署。

Vue 前端通过构建产物由 Spring Boot 静态资源服务提供，用户通过浏览器访问本地工作台。Spring Boot 在本地负责 API、Agent、任务执行与 SQLite 存储。

后续可以打包成安装程序或增加桌面外壳，但不作为首个核心开发目标。

默认只运行一个 DevMate 后端实例，数据库和执行目录加进程锁，避免多实例并发修改工具仓库。

模型服务通过可配置 API 接入；没有配置模型时，环境扫描、项目识别、工具版本检查和手工执行模板仍可使用，智能诊断与自然语言任务规划暂不可用。

## 非功能要求与验收
**正确性：** 在受支持的示例项目中，可以完成从仓库导入到本地启动的完整流程，错误情况有明确提示。

**安全性：** 未经授权不能执行安装或文件修改；恶意提示词不能绕过后端规则；路径越界操作被拒绝。

**可靠性：** 执行失败能够保留日志和任务状态；重新扫描不产生重复安装；取消操作能够终止受管理进程并更新状态。

**可维护性：** 新增开发工具通过 InstallerAdapter 扩展，新增项目类型通过 ProjectDetector 扩展，避免把所有判断写在单一 Agent 类中。

**可观察性：** 每个任务能够查看执行计划、审批记录、步骤状态、执行命令摘要、耗时、退出码及错误日志。

## 开发落地顺序
先完成 Spring Boot、Vue 和 SQLite 的基础工程，以及项目、环境、任务等核心数据模型。

随后实现 EnvironmentScanner、ProjectDetector、EnvironmentResolver，使系统在没有 Agent 的情况下能够识别项目、检查工具版本、生成基础运行建议。

接着实现 PolicyEngine、ApprovalService、TaskScheduler 和 CommandExecutor，完成可审计、可审批的环境安装与项目启动流程。

在确定性执行链路稳定后接入 Spring AI，逐步加入自然语言理解、结构化任务规划、日志诊断和修复建议。

最后补齐日志面板、环境配置管理、任务恢复、安全测试、异常场景和部署打包。

**V1 最小闭环验收标准：**

用户导入一个支持的 Spring Boot 项目，系统自动检查 JDK 和 Maven，识别缺失或不匹配的环境，生成操作计划；用户确认后完成环境准备、依赖安装与项目启动；启动失败时能够读取日志、解释错误、提出修复方案并在再次审批后执行；全过程保留任务和配置变更记录。

只要这条链路完整可运行，DevMate V1 的核心技术架构就成立。
