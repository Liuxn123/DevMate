# DevMate Agent 功能需求文档
**文档版本：** V0.1（讨论稿）  
**目标平台：** Windows 10/11  
**产品类型：** AI 驱动的本地开发环境管理与项目部署工具  
**核心定位：** 以“新项目从 Git 仓库到本地成功运行”为主线，统一完成环境检测、依赖管理、项目配置、启动验证与故障修复。

---

## 一、产品概述
### 1.1 产品目标
DevMate 致力于解决开发人员在本地开发过程中遇到的环境配置繁琐、软件版本混乱、依赖安装分散、项目启动失败和故障排查耗时等问题。

用户只需要提供项目仓库地址或本地项目路径，DevMate 就能够分析项目需要的开发环境，检查本机配置，生成环境搭建计划，在用户确认后执行相关操作，最终帮助项目成功运行。

### 1.2 目标用户
+ Java 后端开发人员
+ 需要维护多个开发项目的程序员
+ 经常切换不同版本开发环境的开发人员
+ 希望快速搭建新项目的开发者

### 1.3 核心设计原则
**统一管理：** 开发工具统一安装到指定仓库，尽可能避免路径散乱。

**项目隔离：** 每个项目维护独立的环境配置，减少不同项目之间的冲突。

**AI 辅助决策：** Agent 负责分析需求、诊断问题和规划解决方案，具体操作通过可控工具执行。

**安全可控：** 涉及安装、修改、删除、执行脚本等操作时，必须经过相应的权限校验和用户确认。

**过程可追踪：** 环境检测、配置变更、命令执行、错误处理均有日志记录。

## 二、核心功能模块
DevMate V1 规划四个核心业务模块，以及两个公共支撑模块。

| 模块 | 核心职责 | V1 优先级 |
| --- | --- | --- |
| 环境管理 | 检测、安装、管理本地开发工具与运行环境 | P0 |
| 项目部署 | 将 Git 仓库或本地项目部署至可运行状态 | P0 |
| 智能诊断与修复 | 分析环境和运行错误，生成并执行修复方案 | P0 |
| 配置管理 | 管理全局工具目录、项目环境与配置文件 | P0 |
| Agent 交互与任务管理 | 自然语言交互、任务规划与执行控制 | P0 |
| 日志与运行记录 | 操作日志、执行历史、问题记录与结果总结 | P1 |


P0 为首版必需功能，P1 为首版增强功能。

## 三、环境管理模块
### 3.1 功能定位
统一管理 Windows 本地开发环境，解决工具安装分散、版本混乱、环境变量配置复杂等问题。

### 3.2 功能需求
| 功能 | 需求描述 | 优先级 |
| --- | --- | --- |
| 环境自动扫描 | 自动识别本机 Git、JDK、Maven 等工具及版本、路径 | P0 |
| 环境状态展示 | 显示工具是否安装、当前版本、安装路径及可用状态 | P0 |
| 开发工具安装 | 将支持的开发工具安装到用户指定目录 | P0 |
| 多版本管理 | 允许同一工具存在多个版本 | P0 |
| 项目环境选择 | 不同项目可以指定使用不同 JDK、Maven 版本 | P0 |
| 环境变量管理 | 检查相关环境变量，优先配置进程级环境 | P0 |
| 工具升级与卸载 | 升级或删除已管理的工具版本 | P1 |
| 环境健康检查 | 检测路径失效、版本冲突、命令不可用等问题 | P0 |
| 依赖缓存管理 | 查看并配置 Maven 等依赖缓存目录 | P1 |


### 3.3 统一工具仓库
用户可以配置统一安装根目录，例如：

```latex
D:\DevMate\
├── tools\
│   ├── jdk\
│   │   ├── jdk-8\
│   │   ├── jdk-17\
│   │   └── jdk-21\
│   ├── maven\
│   │   ├── maven-3.8\
│   │   └── maven-3.9\
│   └── git\
├── cache\
│   └── maven\
└── workspace\
```

该目录为推荐结构，不强制迁移已有安装，也不强制所有工具必须由 DevMate 安装。

**预期效果：** 用户能够清晰了解自己的开发环境，并且在不同项目之间方便地切换版本。

## 四、项目部署模块
### 4.1 功能定位
项目部署是 DevMate 的核心业务入口。

其目标是将传统的：

**拉取代码 → 阅读 README → 安装环境 → 配置依赖 → 修改配置 → 编译 → 启动 → 排查错误**

整合为一个可视化、可监控、可恢复的流程。

### 4.2 功能需求
| 功能 | 需求描述 | 优先级 |
| --- | --- | --- |
| Git 仓库导入 | 根据仓库 URL 拉取项目到指定目录 | P0 |
| 本地项目导入 | 允许直接选择已有项目目录 | P0 |
| 项目结构识别 | 识别 Java 项目、Maven 构建文件及启动入口 | P0 |
| 项目环境分析 | 读取 pom.xml、README 等，提取环境要求 | P0 |
| 环境依赖检查 | 检查 JDK、Maven、数据库连接等是否满足要求 | P0 |
| 环境搭建计划 | 根据检测结果生成待执行步骤及风险提示 | P0 |
| 自动安装依赖 | 经用户确认后安装缺少的开发工具、构建依赖 | P0 |
| 项目配置引导 | 协助配置端口、数据库连接及环境变量 | P0 |
| 项目构建 | 执行 Maven 构建并收集日志 | P0 |
| 项目启动 | 使用适当命令启动项目，跟踪运行状态 | P0 |
| 启动状态验证 | 根据进程、端口、健康接口等验证启动结果 | P0 |
| 多模块项目识别 | 支持更复杂的多模块项目部署 | P1 |
| 项目模板创建 | 根据模板初始化新项目 | P1 |


### 4.3 核心部署流程
```latex
用户输入 Git 仓库地址
          ↓
拉取项目 / 选择本地项目
          ↓
分析项目结构和配置
          ↓
扫描本地开发环境
          ↓
生成环境搭建和启动计划
          ↓
      用户确认
          ↓
安装缺失工具与构建依赖
          ↓
配置项目运行环境
          ↓
项目编译、构建
          ↓
启动项目并验证状态
          ↓
    成功 / 进入智能修复
```

### 4.4 V1 支持范围
首版重点支持：

+ Java / Spring Boot 项目
+ Maven 构建工具
+ Git 仓库与本地目录导入
+ 常用 JDK 版本识别和管理
+ MySQL 连接参数检查与配置引导
+ 单体项目及常规 Maven 多模块项目的基础识别

Gradle、Node.js、Vue、Docker、Redis 自动部署等能力暂列为后续扩展。

**预期效果：** 对于符合支持范围的项目，用户无需手动逐项检查环境，即可在 DevMate 的引导下完成从导入到启动的全过程。

## 五、智能诊断与修复模块
### 5.1 功能定位
利用大模型分析环境异常、构建失败和项目运行错误，并结合工具执行结果提供可操作的修复方案。

这是 DevMate 区别于传统环境管理工具的关键模块。

### 5.2 功能需求
| 功能 | 需求描述 | 优先级 |
| --- | --- | --- |
| 错误自动捕获 | 自动收集构建错误、命令输出、启动异常日志 | P0 |
| 错误智能分析 | Agent 分析错误类型、原因及相关环境信息 | P0 |
| 修复方案生成 | 生成具体修复步骤、操作目标及风险说明 | P0 |
| 自动执行修复 | 经用户确认后调用受控工具执行修复操作 | P0 |
| 修复结果验证 | 重新执行检查或构建，确认故障是否解决 | P0 |
| 失败重试 | 对可恢复的错误提供有上限的重试机制 | P0 |
| 修改前备份 | 修改配置文件前保存原始内容 | P0 |
| 修复记录 | 保存错误信息、修复方法及验证结果 | P1 |
| 常见问题知识库 | 沉淀已处理问题，用于辅助后续诊断 | P1 |


### 5.3 典型使用场景
**场景：JDK 版本不兼容**

用户导入一个需要 JDK 17 的 Spring Boot 项目，但本机当前使用 JDK 8。

DevMate 检测到版本冲突，提示用户选择已有 JDK 17 或安装新版本。确认后自动准备环境，为该项目指定 JDK 17，再重新构建并验证。

**场景：Maven 构建失败**

项目启动时提示依赖解析失败。

Agent 结合 Maven 错误日志、settings.xml 配置、仓库连接情况进行诊断，生成相应的修复方案。

对于修改 Maven 镜像配置、清理指定依赖缓存等操作，在用户确认后执行，并重新进行构建验证。

### 5.4 Agent 修复边界
默认允许在授权范围内处理环境配置、依赖管理、路径错误、工具版本不匹配等问题。

对于 pom.xml、application.yml 等项目配置文件，允许在用户确认并备份后进行受控修改。

默认不修改 Java 等业务源代码，不自动执行不可逆的删除操作，不绕过安全限制。

**预期效果：** 系统不仅能够发现问题，还能给出有依据的修复方案，并通过实际执行结果验证修复是否成功。

## 六、配置管理模块
### 6.1 功能定位
统一管理 DevMate 的全局设置和各项目的独立运行配置，避免用户在不同工具和项目之间反复调整环境。

### 6.2 功能需求
| 功能 | 需求描述 | 优先级 |
| --- | --- | --- |
| 全局路径配置 | 管理工具仓库、缓存、项目工作区等默认路径 | P0 |
| 项目环境配置 | 指定项目使用的 JDK、Maven 等工具版本 | P0 |
| 启动参数配置 | 管理应用端口、运行参数与环境变量 | P0 |
| 配置文件识别 | 识别 pom.xml、application.yml 等文件 | P0 |
| 配置冲突检查 | 检测版本和环境配置之间的冲突 | P0 |
| 配置备份与恢复 | 修改前备份，支持恢复已备份的配置 | P0 |
| 配置方案复用 | 复用现有项目的环境配置 | P1 |
| 配置导入导出 | 导入导出可移植的项目环境描述 | P1 |


### 6.3 配置体系
采用两级配置方式。

**全局配置：** 管理 DevMate 自身使用的工具仓库、下载路径、缓存目录、模型参数和安全执行策略。

**项目级配置：** 管理每个项目独立使用的开发工具版本、运行参数、环境变量及启动命令。

例如：

```yaml
project:
  name: demo-service
  path: D:/Projects/demo-service

environment:
  java: "17"
  maven: "3.9"

build:
  tool: maven
  command: "mvn clean package"

runtime:
  profile: dev
  port: 8080
```

示例为逻辑配置结构，实际字段和文件格式在技术设计阶段确定。账号密码等敏感信息不应直接明文写入可导出的配置文件。

**预期效果：** 不同项目可以采用不同版本的开发环境，同时复用统一工具仓库中的资源。

## 七、Agent 交互与任务管理模块
### 7.1 功能定位
作为 DevMate 的统一交互入口，负责理解用户意图、制定操作计划、调度相关工具并展示执行结果。

### 7.2 功能需求
| 功能 | 需求描述 | 优先级 |
| --- | --- | --- |
| 自然语言输入 | 用户可以使用自然语言描述任务与问题 | P0 |
| 工具调用 | Agent 可以调用环境检测、安装、配置和命令执行工具 | P0 |
| 任务规划 | 将用户目标拆分成可执行步骤 | P0 |
| 执行确认 | 在涉及风险或系统变更的操作前请求用户确认 | P0 |
| 执行进度展示 | 显示当前任务、执行状态与步骤结果 | P0 |
| 任务失败处理 | 记录失败步骤，允许用户修正后继续执行 | P0 |
| 历史任务查看 | 查看过去执行的任务和结果 | P1 |
| 多轮上下文 | 支持围绕同一故障进行连续分析与修复 | P1 |


Agent 不直接依赖大模型生成的任意命令进行无限制执行，而是优先调用具有明确输入、输出和权限边界的工具。

## 十一、核心验收场景
**场景 A：新项目部署成功**

用户输入一个公开的 Spring Boot Maven 项目仓库地址，选择目标目录。DevMate 完成项目分析、环境检测，生成操作计划，并在用户确认后完成缺失工具准备、依赖构建和项目启动。

验收要求：能够展示完整执行记录，并通过进程、端口或健康检查确认项目处于正常运行状态。

**场景 B：本地环境版本冲突**

用户已有 JDK 8，但项目要求 JDK 17。

DevMate 应检测冲突，使用已有或新安装的 JDK 17，并在不破坏其他项目配置的情况下运行当前项目。

验收要求：目标项目构建成功，其他项目原有环境配置保持不变。

**场景 C：构建失败后的智能修复**

项目因 Maven 配置或环境问题无法正常构建。

DevMate 捕获错误、分析原因、提出修复方案，经确认后执行，再次构建并验证结果。

验收要求：能够展示问题证据、执行的修复操作及验证结果；若无法修复，应明确报告失败原因，而非虚报成功。

**场景 D：配置修改与恢复**

用户确认 Agent 修改项目配置文件。

DevMate 修改前创建备份，记录变更内容，并提供恢复原始文件的能力。

验收要求：在目标文件未被外部再次修改的前提下，能够正确恢复修改前的内容。

## 十二、后续版本方向
**V1：最小可用产品**

打通 Java 项目从仓库导入、环境准备、构建启动到错误修复的完整闭环。

**V1.1：使用体验完善**

增加 Node.js、Gradle 等环境支持，完善依赖缓存管理、配置方案复用及项目历史管理。

**V2：开发环境智能管家**

扩展更多开发工具、环境健康扫描、问题知识库、项目模板、跨项目环境优化等能力。

**V3：可选高级扩展**

根据真实用户需求再考虑 Docker、远程开发环境、团队共享配置等功能。

## 十三、产品最终目标
DevMate 的长期目标不是简单地将常用系统命令包装成一个聊天界面，而是形成一个完整的本地开发环境生命周期管理工具。

通过统一工具仓库、项目级环境隔离、Agent 任务规划、受控工具调用、错误诊断和修复验证，降低开发者从获取项目代码到成功运行项目的时间成本。

**V1 最重要的交付目标：让一个符合支持范围的 Java 项目，从仓库地址开始，在 DevMate 中完成环境搭建、项目启动以及常见环境故障修复的全流程。**
